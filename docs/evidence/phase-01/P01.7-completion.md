## What was implemented

1. **Event Registry** (`platform/events/index.mjs`)
   - Versioned event-type registration in `platform_events`.
   - Schema validation for event descriptors (`event_type`, `module_id`, `schema_version`, `delivery_guarantee`, `privacy_classification`).
   - Payload schema validation against required fields.
   - Tenant/company scope flags per event type.
   - Module ownership validation (module must be enabled).

2. **Transactional Outbox Dispatcher** (`platform/outbox/index.mjs`)
   - Polls `platform_outbox` for pending/failed rows scheduled for delivery.
   - Registers in-process consumers by event type.
   - Delivers each event to all consumers inside a per-row transaction.
   - Retries up to `maxAttempts` with explicit state transitions (`pending` → `failed`/`delivered`/`dead`).
   - Dead-letter retrieval and explicit replay.
   - No-consumer events are marked `delivered` so the outbox does not accumulate orphan rows.
   - Preserves the business commit: outbox delivery failure does not roll back the already committed business transaction.

3. **Audit integration**
   - Every action, lifecycle transition, entity registration, view registration, and feature-flag change writes to `platform_audit_log`.
   - Audit rows include actor, tenant/company/branch, correlation ID, source channel, before/after values, and result.
   - Action executor writes both action-specific audit (`action.create`) and generic command audit (`action.execute.{actionId}`).

4. **Provenance links**
   - Correlation IDs connect API request → command → audit → outbox → integration delivery.
   - Outbox rows carry aggregate ID, module ID, actor, and correlation ID.
   - Action executor records `before_value`/`after_value` for transitions and creates.

## Risks and decisions

1. **In-process consumers only**: Phase 01 uses in-process handlers for outbox delivery. A durable worker topology, external webhooks, and credential vault are deferred.
2. **Sensitive-field redaction**: The privacy classification vocabulary is registered but policy hooks for redaction/hashing are deferred to Phase 02/08.
3. **Ordering**: Events are polled in `created_at` order. Per-stream ordering policies and explicit partition keys are deferred.
4. **Delivery semantics**: `at-least-once` is the default. Exactly-once semantics rely on consumer idempotency and the outbox replay audit trail.
5. **No external side effects in business transaction**: Consumers run after the business commit, inside their own outbox transaction, so a consumer failure cannot roll back the authoritative state change.
