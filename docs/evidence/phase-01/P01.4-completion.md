## What was implemented

1. **Document Lifecycle** (`platform/governance/document-state/index.mjs`)
   - State definition registration with full-graph validation and reachability checks.
   - Per-record state tracking (`x_doc_states`) and transition history (`x_doc_state_history`).
   - `transition`, `reverse`, and `amend` operations with optimistic version checks.
   - Terminal/immutable state detection used to block generic CRUD writes.
   - Arabic error messages and server-derived execution context.
   - Audit + outbox evidence on every lifecycle event.

2. **Action Registry & Executor** (`platform/kernel/actions/index.mjs`)
   - `ActionRegistry` persists actions in `platform_actions` with module ownership validation.
   - `ActionExecutor` executes registered actions inside a transaction boundary.
   - Supported action kinds: `lifecycle_transition`, `create`, `reverse`, `amend`, `domain`.
   - Input schema validation, precondition evaluation, and idempotency enforcement.
   - Idempotency table `action_idempotency` with payload-hash mismatch detection.
   - Audit and outbox evidence written atomically with the action result.
   - Domain handlers registered by module code (clean extension point).

3. **Repository integration** (`platform/data/repositories/index.mjs`)
   - Repository registers a default lifecycle guard that rejects `update`/`delete` on terminal/immutable states.
   - Works alongside the existing `lifecycle_policy` generic-mutation denial.

4. **Migration 003** (`database/migrations/003_platform_kernel_actions_and_lifecycle.mjs`)
   - Creates `x_doc_state_defs`, `x_doc_states`, `x_doc_state_history`, `action_idempotency`.
   - Adds `kind` column to `platform_actions`.
   - Seeds a `crm_lead` lifecycle (draft → submitted → approved → cancelled) with submit, approve, cancel, reverse_approval, and amend actions.

## Risks and decisions

1. **Domain handler extension point**: `domain` actions require a handler to be registered at runtime. This prevents generic code from executing arbitrary business logic and keeps the action executor a dispatcher.
2. **Action audit action naming**: Unified as `action.execute.{actionId}` plus internal action-specific rows (e.g., `action.create`). This gives both a uniform command trace and a fine-grained lifecycle trace.
3. **Terminal-state guard on generic entities**: The repository guard applies to any entity that has a terminal state, even if its `lifecycle_policy` is `generic`. This is intentional because the guard is about document state, not registry policy.
4. **Cancel from draft**: Added to the seeded `crm_lead` lifecycle to allow the cancel-vs-reverse demonstration. Business rules may restrict this later per domain.
5. **Payroll/Attendance**: No changes. Lifecycle and action examples use `crm_lead` (non-financial).
