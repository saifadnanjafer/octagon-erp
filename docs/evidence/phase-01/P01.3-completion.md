## What was implemented

1. **Entity descriptor schema** (`platform/kernel/entities/schemas/entity-descriptor.mjs`)
   - Validates `id`, `module_id`, `storage_owner`, `primary_key`, `label_ar`, fields, and relations.
   - Enforces governance enums: scope, lifecycle_policy, query_policy, action_policy, customization_policy, history_policy.
   - Supports the legacy `entities.json` field shape (object keyed by field name) and normalizes it.
   - Row/Descriptor bidirectional conversion.

2. **Entity Registry** (`platform/kernel/entities/index.mjs`)
   - Persists descriptors in `platform_entities`.
   - `register`, `get`, `list`, `listByModule`, `unregister`, `loadFromFile`.
   - Reserves platform table names and requires the owning module to be installed and enabled.
   - Writes to `platform_audit_log` on registration/unregistration.
   - Ships a default entity set in `platform/kernel/entities/default-entities.json`.

3. **Sequence authority** (`platform/records/sequences/index.mjs`)
   - Template formatting: `{YYYY}`, `{MM}`, `{DD}`, `{PERIOD}`, `{#####}`.
   - Counter storage in `platform_sequences` keyed by `scopeKey:companyId:period`.
   - Reset policies: none, fiscal_year, calendar_year, calendar_month.
   - Transaction-neutral (caller manages the transaction boundary) so it can be composed inside repository writes.

4. **Repository abstraction** (`platform/data/repositories/index.mjs`)
   - Bounded list/read/summary for all governed entities.
   - Generic `create`, `update`, `delete` **only** when `lifecycle_policy === 'generic'`.
   - Protected entities (`workflow`, `state_machine`, `immutable`, `append_only`) reject generic mutation.
   - Server-derived execution context: `tenantId`, `companyId`, `branchId`, `userId`, `actorType`, `correlationId`, `sourceChannel`, `now`.
   - Company scope enforcement via `company_id`.
   - Defaults, sequence assignment, optimistic `version` checks, write guards.
   - Dual audit: `x_audit` (record-level history) and `platform_audit_log` (action-level).
   - `onWrite` subscribers and `registerGuard` hooks for workflow/outbox integration.
   - Declared relation expand (`readWithRelations`) through repositories, not ad-hoc joins.

5. **Legacy JSON adapter** (`platform/data/repositories/legacy-adapter.mjs`)
   - Read-only bridge to legacy `database.json` style collections.
   - Presents legacy records with the same document shape as `x_records`.
   - Explicitly denies create/update/delete.

6. **Migration 002** (`database/migrations/002_platform_kernel_entities_and_storage.mjs`)
   - Creates `x_records`, `x_audit`, `x_sequences`, `x_chatter`, `x_followers`, `x_views`, `x_custom_fields`, `x_notifications`, `x_approvals`.
   - Seeds `platform_kernel` module as enabled.
   - Seeds `platform_entities` rows from `default-entities.json`.

7. **Migration 001 amendment** (`database/migrations/001_platform_kernel_bootstrap.mjs`)
   - Added `section`, `sequence`, `seq_field`, `chatter`, `acl`, `status_key` columns to `platform_entities` so the legacy entity surface can be stored canonically.
   - Not yet applied to any production database; only exercised on disposable test databases.

## Risks and decisions

1. **Sequence transaction policy**: `nextSeq` was changed from self-managed transaction to caller-managed so it can be composed inside repository `create`. This preserves atomicity but requires all future callers to provide a transaction boundary. This is acceptable because sequences are always issued as part of a write operation.
2. **`platform_entities` schema amendment**: Migration 001 was amended to add legacy-surface columns (`sequence`, `seq_field`, `status_key`, `acl`, `chatter`, `section`) before the migration is applied to production. This is safe because Phase 01 only uses disposable test databases and `database.db` is not touched.
3. **Module uninstall scope**: ModuleRegistry now blocks uninstall when platform artifacts (entities, actions, views, settings, events, sequences) reference the module, preventing FK violations and data loss.
4. **RepositoryFactory caching**: Uses a WeakMap keyed by dialect instance so closed databases do not poison the cache. This avoids the "database is not open" error when multiple test databases are used sequentially.
5. **ACL / masking**: Field-level ACL and actor scope are not implemented here; they are Phase 02 responsibilities. The repository accepts `userId` and `companyId` but does not apply permission tables.
6. **Payroll / Attendance**: No changes to payroll, attendance, or employee records. The legacy adapter is read-only and does not touch these collections.
7. **Known missing donor paths**: `erp-research/frappe-develop` and `erp-research/yudao-ui-admin-vue3-master` remain absent. Frappe/RuoYi frontend patterns are inferred from available references or deferred.
